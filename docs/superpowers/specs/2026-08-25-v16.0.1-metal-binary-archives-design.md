# v16.0.1 Apple Silicon Metal Binary Archive Hot-fix

## Context

The v16 AIR 2.6 compatibility hot-fix reduced the Metal IR toolchain requirement,
but the reporter's M1 Max on macOS Tahoe still terminates `MTLCompilerService`
while Metal creates specialized pipeline state objects for `workerHmac_seq` and
`workerBip38Grouped`. The failure happens before dispatch and is reported as
`XPC_ERROR_CONNECTION_INTERRUPTED`; it is not a BIP32 derivation failure.

v16.0.1 will bypass that runtime compiler path for the affected specializations
by embedding native Metal binary-archive entries for every Apple Silicon GPU
architecture supported by the current toolchain. The AIR 2.6 metallib remains
embedded as the compatibility fallback for every other pipeline.

## Scope

The archive contains the three pipeline specializations needed by the affected
code paths:

1. `workerHmac_seq` with the exact compressed BIP32 function-constant profile
   used by the issue reproduction command.
2. `workerBip38Grouped` with BIP38 non-EC profile 28.
3. `workerBip38Grouped` with BIP38 EC profile 30.

All three entries use the production secp256k1 precompute configuration
(`windowBits=16`, `windows=17`). The build-time configuration will be checked
against the constants bound by the host runtime so an archive entry cannot
silently drift from its matching pipeline key.

Each entry is compiled for exactly these 11 Apple Silicon GPU slices:

- `applegpu_g13g`, `applegpu_g13s`, `applegpu_g13d`
- `applegpu_g14g`, `applegpu_g14s`, `applegpu_g14d`
- `applegpu_g15g`, `applegpu_g15s`, `applegpu_g15d`
- `applegpu_g16g`, `applegpu_g16s`

AMD and Intel GPU slices are excluded because the release executable is arm64
and this hot-fix targets Apple Silicon. Precompiling every exported Metal kernel
is explicitly out of scope: it would multiply archive size and specialization
maintenance without evidence that those pipelines trigger the reported crash.

## Build and embedding

A deterministic build script will generate the three function-constant records,
compile their native archive entries for each of the 11 slices, combine them into
one universal archive, and reject duplicate, missing, or unexpected slices. The
archive is linked into the executable as `__DATA,__metalarc`, alongside the
existing AIR 2.6 `__DATA,__metallib` section.

The regular metallib remains targeted at macOS 14/AIR 2.6. The arm64 executable
continues to require macOS 15. Packaging checks will reject a build unless it has:

- executable version `v16.0.1`, arm64 architecture, and minimum macOS 15;
- AIR 2.6/platform 14 embedded metallib;
- both `__DATA,__metallib` and `__DATA,__metalarc` sections;
- exactly the 11 expected Apple GPU archive slices and no Intel/AMD slices.

## Runtime behavior

At initialization, the runtime reads the embedded archive bytes, materializes
them to a private temporary file required by `MTLBinaryArchiveDescriptor`, opens
one retained `MTLBinaryArchive`, and removes the temporary file after Metal has
successfully loaded it. File creation and cleanup failures are reported without
removing the existing AIR fallback.

For `workerHmac_seq` and `workerBip38Grouped`, pipeline creation uses an
`MTLComputePipelineDescriptor` with `binaryArchives` and first requests
`MTLPipelineOptionFailOnBinaryArchiveMiss`. A successful request proves that
Metal selected a native archive entry and emits a one-time diagnostic naming the
function. An archive miss or archive-load failure falls back to the current AIR
pipeline creation path so unaffected commands and unarchived specializations
retain existing behavior. If both paths fail, the diagnostic includes the
archive error and the compiler error.

The existing pipeline cache remains authoritative after creation. Buffer
bindings, dispatch geometry, function constants, and kernel code are unchanged.

## Verification

The release must pass from a clean checkout:

- archive configuration validation and an exact 11-slice inspection;
- clean executable, metallib, archive, and release-package builds;
- a forced archive-hit run on the local Apple GPU for each of the three entries,
  where fallback is treated as a test failure;
- the exact issue BIP32 command with all three derivations and no
  `XPC_ERROR_CONNECTION_INTERRUPTED`;
- BIP38 non-EC and EC smoke/correctness coverage;
- `illbloom-prng-test`, BLS vectors, packaging checks, and existing release
  smoke tests;
- arm64/minOS 15, AIR 2.6/platform 14, both embedded sections, executable
  version, archive slices, and SHA-256 assertions.

Local validation on the available M4 proves the g16s archive path. Slice
inspection proves that all 11 native payloads are present, but final M1 behavior
still requires confirmation from the issue reporter because no local M1 host is
available.

## Performance and compatibility

Steady-state kernel throughput is expected to remain unchanged because the
native archive contains the same specialized functions and does not alter GPU
dispatch. First pipeline creation should become faster and more reliable by
avoiding JIT compilation. Costs are limited to executable size and a one-time
startup extraction/load of the embedded archive; both will be measured and
reported before publication.

## Publication and rollback

The production change will be committed to `main`, tagged `v16.0.1`, and
published as a new GitHub Release. The existing `v16` tag and v16 assets will not
be moved or overwritten. The new release will contain:

- `METAL_CRYPTO_TOOLKIT-v16.0.1-macos-arm64.tar.gz`
- `METAL_CRYPTO_TOOLKIT-v16.0.1-macos-arm64.tar.gz.sha256`

The uploaded archive will be downloaded again, checksum-verified, inspected,
and smoke-tested before announcing the fix. If any round-trip verification
fails, the v16.0.1 release will not be announced and the issue will not receive a
success reply.

After successful verification, issue #1 will receive an English reply explaining
the remaining runtime-compiler failure, linking the exact hot-fix commit and
v16.0.1 asset, providing its SHA-256, asking the reporter to retry on M1, and
stating that the issue remains open until that confirmation.
